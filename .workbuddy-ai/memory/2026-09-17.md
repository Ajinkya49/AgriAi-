### ⚠️ Lesson: adding `loading.tsx` broke the e2e suites — correctly

Streaming skeletons meant the suites were reading the **skeleton**, not the page.
Three auth and six community assertions failed. Two fixes, both making the tests
more honest:

- a `readBody()` helper that waits for `[data-testid="loading"]` to clear;
- `textContent` → **`innerText`** (visible text only — `textContent` was picking up
  the RSC payload in `<script>` tags).

**And:** `innerText` applies CSS `text-transform`, so the uppercased crop label
reads "TOMATO" — that assertion had to become case-insensitive.

## Session 12: Phase 9 (Testing) — complete

### ⚠️ Found and fixed: the most serious bug in the project

The expert-confirmation prompt was gated on `!diagnosis.is_healthy`. A flat grey
image returns **`Tomato - Healthy` at 26% confidence** (below the 0.30 reliability
floor), so the screen said *"No disease symptoms were detected"* with **no warning
at all**. A farmer photographing a sick crop could be told it looked fine.

Fixed: the prompt now shows whenever `needs_expert_confirmation`, and the "healthy"
message is only reassuring at **high** confidence.

Only Phase 9's explicit "test the low-confidence flow" item found this.

### ⚠️ Known limitation (recorded, not fixed)

**The model is confidently wrong on pure random noise** — `Tomato - Healthy` at
**94.1%** on an image with no leaf in it. Out-of-distribution rejection needs work
before launch. Probing table in DECISIONS §9.2.

### ⚠️ A near-miss that was a test bug, not a security hole

My new cross-user delete probe reported "POST WAS DELETED". It was the probe:
`posts_select_authenticated` makes the feed **public**, so an unfiltered query
returned the attacker's own post. Fixed by filtering on `user_id` — and
strengthened to assert the post **survives**, because PostgREST returns **204** for
a delete matching zero rows, so the status code proves nothing.

## Session 13: Phase 10 (Deploy) — configuration complete, deploy pending

### ⚠️ What could NOT be done

**The actual deploy needs the user's Vercel / Render / Supabase accounts.** Docker
is not available in this environment either, so **the image was never built or
run**. The final "Done when" (a real user completing the journey on the production
URL) cannot be signed off. Everything up to that line is done and verified.

### ⚠️ The central problem solved: ML artefacts vs .gitignore

`.gitignore` excluded `*.pt` and `backend/app/rag/index/`. A deploy from a clean
clone would have shipped **a container with no model and no index** — both
`/api/diagnose` and the assistant returning 503 with no obvious cause, because
there is nowhere to download a *locally trained* model from.

Fixed with explicit negations for the three files (16 MB + 892 KB + 52 KB), and
**the Dockerfile fails the build if any is missing**.

### Also fixed

`.env.example` set `GEMINI_MODEL` **twice** — a leftover Phase 1
`gemini-1.5-flash` (404s for new keys) came last, so copying the example gave a
dead assistant. Now single-valued.

### Key decisions

1. **Artefacts committed** (a reversal of the original gitignore policy), because
   a self-trained model has no remote source.
2. **One uvicorn worker** — extra workers multiply memory without throughput, and
   each loads its own model copy. Scale the instance instead.
3. **Config problems are reported, not fatal** — a container that dies on boot
   tells an operator less than one that boots and reports exactly what is wrong.
   It specifically catches the two CORS mistakes, which fail *silently in the
   browser*.
