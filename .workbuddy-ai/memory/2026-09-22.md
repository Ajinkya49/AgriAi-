# 2026-09-22

## Crop picker vs model scope — fixed, with a guard

The bug: the picker offered **12** crops; the model could diagnose **3**
(Tomato, Potato, Pepper). `Pepper` was diagnosable but **missing from the picker
entirely**. A farmer growing Rice could declare it, photograph a leaf, and get a
confident-looking answer for whichever of the 10 trained classes scored highest —
a fixed-output-layer classifier cannot say "not one of mine". Nothing errored.

### What changed

- **`backend/app/models/labels.py`** — added `DIAGNOSABLE_CROPS` **derived** from
  `DISEASE_CLASSES` (not hand-listed, so it cannot drift from the checkpoint),
  plus `is_diagnosable_crop()` (case-insensitive) and `diseases_for_crop()`.
- **`backend/app/api/routes/health.py`** — `/health/dependencies` now reports
  `model.diagnosable_crops`, so the app can read the real scope at runtime.
- **`frontend/lib/validation/auth.ts`** — added `DIAGNOSABLE_CROPS`,
  `isDiagnosableCrop()`, and `CROP_OPTIONS_ORDERED` (diagnosable first). Added
  `Pepper` to `CROP_OPTIONS`. `CROP_OPTIONS` stays a **superset** on purpose:
  farmers declare what they grow, not what v1 can diagnose.
- **Crop pickers** (`onboarding-form.tsx`, `settings-form.tsx`) — ordered list,
  tick + `sr-only` "photo check available" on diagnosable crops.
- **`app/(app)/upload/page.tsx`** — states the real scope *before* a photo is
  spent, and points unsupported crops at the assistant instead. The assistant
  handles any crop; only photo checking is limited.
- **`backend/tests/test_crop_coverage.py`** — new, 9 tests. Parses the frontend
  `.ts` source rather than duplicating the list, so it compares the two real
  definitions.

### Verified

- 9/9 new tests pass; full backend suite **70 passed**.
- **Confirmed the guard can fail** by temporarily reintroducing the original bug
  (removed `Pepper`) → `test_frontend_picker_offers_every_diagnosable_crop` failed
  with `['pepper']`. A guard that cannot fail is worthless, so this mattered.
- Frontend typecheck + lint clean.

## Regional outbreak alerts — new feature, shipped to live

The first feature built from the "what should farmers get next" list. Reads as a
banner on the dashboard when a disease is spreading nearby.

### Why it's the right first feature

`diagnoses` RLS is per-user, so a farmer can only ever see their own rows. The
**aggregate** is genuinely different information: three neighbours independently
finding Late Blight in one fortnight is a signal none of them can see alone. It
costs no new infrastructure — the data already existed.

### The design decision that mattered

Thresholding on **rows** would have been wrong. Live data proved it: Maharashtra
had **132 qualifying reports from exactly ONE farmer** (testing), which would
have fired a massive false outbreak alert. The threshold counts **distinct
farmers**, so live correctly returns **0 rows**.

A false outbreak alert is worse than no alert — it makes farmers spray a healthy
field. Hence: distinct-farmer floor of 3, Healthy excluded, confidence ≥ 0.30
(matching `CONFIDENCE_UNRELIABLE_THRESHOLD`).

### Privacy

`public.regional_outbreaks(p_days, p_min_reports)` is SECURITY DEFINER (it must
read past RLS), so the guards carry the weight:
- returns **counts only** — no `user_id`, `image_url`, `id`, `confidence_score`
- **caller's own region only**, read from their own profile
- **hard floor of 3 distinct farmers**, clamped inside the function so
  `p_min_reports => 1` cannot lower it. Verified: `min_reports=1` → still 0 rows.
- `anon` revoked — confirmed live: `401 42501 permission denied`

### Files

- `supabase/migrations/20260922000001_regional_outbreaks.sql` — the function, plus
  a verification `DO` block asserting no identifying column appears in
  `pg_get_function_result()` and that the default floor is still 3.
- `frontend/lib/outbreaks.ts` — RPC wrapper. **Never throws**; a failed alert
  degrades to no alert, because a farmer must still see their history.
- `frontend/components/diagnosis/outbreak-alert.tsx` — banner. Renders nothing
  when empty (a "nothing to report" banner trains people to ignore it), and is
  not dismissible (it only appears when something is genuinely spreading).
- `frontend/app/(app)/dashboard/page.tsx` — runs the outbreak query concurrently
  with the history query via `Promise.all`.
- `supabase/tests/run_outbreak_tests.py` — 20 tests, mostly adversarial.
- `frontend/app/globals.css` — new `--color-warning*` tier. Deliberately separate
  from `--color-danger*`, which is reserved for genuine failures.

**Applied to live** via `apply_migrations.py` (ledger showed exactly 1 pending).
Verified live: signature has no identifying columns, `anon` blocked,
`authenticated` allowed, new index present, RPC returns 200 via PostgREST.

### Two bugs found while building

1. `having count(*) >= b.min_reports` failed — a cross-joined CTE column isn't in
   the `GROUP BY`. Fixed with scalar subqueries.
2. My first verification block checked `information_schema.columns`, which only
   covers tables/views — **functions are not there**, so the guard could never
   fail. Rewritten against `pg_get_function_result()`.

Also: `app/__preview-outbreak/` was never routable — Next treats `_`-prefixed
folders as private. Renamed to verify, then deleted.

### Not done, on purpose

No FastAPI route. The dashboard reads its own data directly via Supabase (same
shape as the existing `diagnoses` query), so routing this through the backend
would add a hop and make a banner depend on the API being warm (~8.5 s cold
start). The aggregate belongs in SQL.
