`NEXT_PUBLIC_SUPABASE_ANON_KEY` in the Vercel dashboard. `NEXT_PUBLIC_*` is baked
at **build** time — changing one needs a redeploy.

slash — it silently fails to match and looks like a network error.

`Permissions-Policy: camera=(self), geolocation=(), microphone=()`. Camera is right.

## Clerk migration — DB layer DONE and verified on live

Applied `20260920000001_clerk_compatible_identity.sql` to the live Supabase
project. **Supabase Auth still works** — the whole point of the design.

### The key design decision: a dual-compatible identity helper

Instead of swapping to Clerk's identity outright, added:

```sql
create or replace function public.current_user_id() returns text
language sql stable as $$
  select coalesce(
    nullif(current_setting('request.jwt.claim.sub', true), ''),
    (nullif(current_setting('request.jwt.claims', true), '')::jsonb ->> 'sub')
  );
$$;
```

**Returns the raw `sub` as TEXT, with no cast** — the one thing `auth.uid()` gets
wrong for Clerk. Correct for both issuers:
`Supabase -> 'a1b2c3d4-...'` and `Clerk -> 'user_2abc...'`.

Because both are text, `users.id = current_user_id()` works either way. So the
app keeps running on Supabase and the Clerk switch becomes a dashboard toggle
rather than a big-bang cutover.

### What changed (live)

`users.id` uuid→text · **6** `user_id` columns · **28** policies rewritten ·
`auth.users` FK dropped · `public_profiles(uuid[])` → `(text[])` · 8 test calls
updated.

Live verified: `users.id`=text, 6 text `user_id` cols, **0** policies on
`auth.uid()`, **28** on `current_user_id()`, 5 users preserved.

### ⚠️ Two Postgres rules the local harness caught (both would have hit live)

1. **`cannot alter type of a column used in a policy definition`** — policies must
   be DROPPED before the type change, then recreated.
2. **`foreign key ... cannot be implemented: uuid and text`** — doing
   drop/alter/add per table fails on the second table, because `users.id` is
   already text while that table's column is still uuid. Fix: drop **all** FKs,
   alter **all** columns, recreate **all** FKs. Three explicit phases.

Neither was visible by reading the SQL. **Testing against embedded Postgres first
is what caught them** — this is the strongest argument for that harness existing.

### Tooling added

- `supabase/scripts/generate_clerk_migration.py` — regenerates the migration from
  the *deployed* policy definitions. 28 policies is too many to transcribe; a typo
  in an RLS policy is a data leak, not a bug.
- `supabase/scripts/apply_migrations.py` — applies pending migrations to live with
  a `schema_migrations` ledger, one transaction each, `--dry-run`/`--baseline`.
  **This did not exist before; the live schema had been drifting from the repo.**
- `supabase/scripts/bootstrap_migration_ledger.py` — one-time: verifies migrations
  1-5 really are applied (by checking a distinctive object from each) before
  recording them, so baselining cannot hide a missing schema.
- `supabase/scripts/snapshot_live_data.py` — 726 rows across 10 tables.

## Clerk — steps 4, 6, 7 done

Owner asked for the remaining Clerk steps. Three of five are done; the app runs on
Supabase Auth throughout.

### Step 4 — backend identity, done WITHOUT a JWT library

`security.py` called `GET /auth/v1/user`, which is GoTrue's own endpoint and only
accepts **Supabase-issued** tokens — so it would reject a Clerk session outright.

Instead of adding a JWT library + JWKS fetching + the Clerk domain in the backend,
it now calls `POST /rest/v1/rpc/ensure_profile` with the caller's own token.
Supabase verifies the signature. Works for both issuers, no new dependencies.

**And it is the same path RLS uses** — if identity resolves here, that subject is
what `public.current_user_id()` sees in every policy. Stronger than verifying
against a different system and hoping they agree.

Proved against live with `backend/scripts/verify_identity_resolution.py`: GoTrue
and PostgREST agree on the subject, bogus token → 401.

`email`/`phone` now come from the profile row, not the auth payload — the row is
the app's own record and identical for either issuer.

### Step 6 — `ensure_profile()`, a lazy upsert

`on_auth_user_created` fires on `auth.users` inserts; with Clerk there is no such
row, so **nothing would create the profile** and every policy would deny.

Chose a lazy upsert over a webhook: no public endpoint, no signing secret, no
retry handling, self-heals on the next request. SECURITY DEFINER but not abusable
— it only inserts a row whose id is the **caller's own** subject from their own
verified JWT; there is no parameter for someone else's id.

**⚠️ Clerk's default session token has NO email claim** (only sub/iss/exp/sid/azp),
and `users_email_or_phone_check` requires email or phone — so row creation is
skipped until an `email` claim is added (Clerk Dashboard → Sessions → Customize
session token). It returns the subject anyway rather than raising; a broken API is
a worse failure than an unknown caller.

### Step 7 — duplicate routes removed

`clerk init` had created `app/sign-in/` + `app/sign-up/`, orphaned and duplicating
`/login` + `/signup`. Removed; `/sign-in` now 404s, `/login` still 200.

**Kept on purpose:** `@clerk/nextjs`, `ClerkProvider`, the 5 `NEXT_PUBLIC_CLERK_*`
vars — inert without a key, and removing them means re-running init later.

### ⚠️ Step 5 (`proxy.ts`) written but NOT applied — deliberately

The change is understood, but applying it now means editing the **auth path of a
working app with no way to test it**, since Clerk isn't configured. An untestable
change to authentication is exactly the risk worth deferring. It needs Clerk's
middleware *composed* with the existing Supabase `updateSession`, plus
`'/__clerk/:path*'` in the matcher — and `clerk init` skipped the file itself
("unsupported shape for automatic Clerk composition").
