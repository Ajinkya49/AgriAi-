## Narrowed the expert-confirmation prompt

The owner reported a "The model is not fully certain — confirm with your local KVK"
panel on a 47.6% result and asked for it to be removed.

**Root cause:** `needs_expert_confirmation` was gated on
`CONFIDENCE_HIGH_THRESHOLD` (0.70), so the panel fired on *every* result below 70%.
On a 10-class problem a 69% call is solid, so the prompt was wallpaper — which
stops it being read at all.

**Change:** gate it on `CONFIDENCE_LOW_THRESHOLD` (0.45) instead, in both places
that compute it — `models/inference.py` and `schemas/diagnosis.py`. Those two must
agree or a result changes shape between creation and re-display. Updated the
backend test that pinned the old behaviour.

Medium confidence is still signalled (amber bar + "Medium confidence" label). The
constraint holds: <45% still prompts expert confirmation.

Verified end to end by re-uploading the actual image — 47%, Medium, **no banner**.
`edge-cases` still passes both directions (25.9% shows it, 99.2% doesn't).

## ⚠️ The image was a rose leaf — so the confidence was left alone

The owner also asked to "increase the confidence". Before touching a number I
pulled the image back out of Supabase storage and looked at it.

**It is a rose leaf.** Serrated margins, rose black spot — concentric-ring lesions
with yellow halos. The model has no rose class; the ten classes are tomato, potato
and pepper only.

| Image | Prediction | Confidence |
|---|---|---|
| The upload (rose) | Early Blight | **47.6%** (runner-up Bacterial Spot 35%) |
| Real `Potato___Early_blight` ×3 | Early Blight | 95.6% / 99.3% / 94.6% |

Mean confidence across the 110 live diagnoses is **86%**. The model is not
underconfident, and 47.6% is honest — it was shown a plant it was never trained on
and it hedged, with the top two classes nearly tied.

**So the confidence was not changed.** Inflating it would manufacture certainty on
an out-of-distribution input — the failure mode constraints #1 and #3 exist to
prevent. The real defect is that the model answers at all for a leaf it cannot
know (the OOD gap in DECISIONS §9.2).

Suggested next step, not implemented: the **top-1 vs top-2 margin** separates the
two cases cleanly (0.13 for the rose leaf vs ~0.93 for a real potato leaf) and
would let the UI say "this doesn't look like a tomato, potato or pepper leaf"
rather than naming a disease. That is a new signal, not a re-scaled one.

## Assistant moved to OpenRouter + Hindi support

Owner supplied an OpenRouter key and asked for the assistant to run on it, and for
Hindi questions to work for farmers who don't read English.

### Provider

OpenRouter is now the **primary** chat provider, Gemini the fallback. Relaxes
constraint #4 ("no multiple LLM providers") — recorded in `DECISIONS.md`. The
provider chain already existed within Gemini, so it's the same pattern. Embeddings
stay on Gemini (the FAISS index was built with `gemini-embedding-001`; changing it
means rebuilding). Constraint #1 untouched.

**⚠️ The first model IDs I wrote were invented and do not exist.** `.env` overrides
`config.py` defaults, so the bad values silently won. Probed the live catalogue and
tested each candidate on the real task:

| Model | Result |
|---|---|
| `deepseek/deepseek-v4-flash-0731:free` | primary — Hindi 91%, grounding + refusal correct |
| `nvidia/nemotron-3-ultra-550b-a55b:free` | fallback — Hindi 100% |
| `google/gemma-4-31b-it:free` | fallback — 429 at test time |

Free-tier limits are **per model**, which is why the chain matters.

### Hindi

Two mechanisms, on purpose: the **model** picks the answer language (covers
romanised Hindi, which no script check can catch); **code** picks the refusal
wording (`detect_language` → `REFUSAL_BY_LANGUAGE`), so a farmer never gets an
English "I don't know".

**⚠️ Two refusal paths, and I only fixed one at first.** The no-retrieval
short-circuit is in `pipeline.py`, not `llm.py`, and had its own English string. A
Hindi farmer asking an off-topic question would have been refused in English.

UI: a language toggle in the assistant switching starter chips, placeholder and
help text. Both suggestion sets ship in one response so switching is instant.

### Three bugs found and fixed on the way

- **`available` reported the assistant as down.** `GET /api/assistant/status` used
  `bool(settings.gemini_api_key)`; with OpenRouter primary and Gemini unset it would
  claim unavailability while working. Now `is_rag_configured`.
- **A test caught a real miss**: `generate_answer` set the refusal *text* from the
  detected language but never passed the `language` field, so every Hindi refusal
  was mislabelled `"en"`.
- **The composer sat underneath the tab bar.** Found by screenshotting the Hindi UI:
  with a long transcript the sticky composer parked at `bottom-20` (80px) under a
  **101px** bar. Both now derive from one `--app-nav-height` token, and `ui-audit`
  asserts it clears the measured bar. (Measuring an empty chat proves nothing — the
  composer only reaches its offset once content pushes it there.)

## Assistant latency — measured, two fixed, one reverted

Baseline was bad: median 18.6s, max 58.2s, **1 failure in 5**.

Added `backend/scripts/time_assistant.py` to measure it properly (real retrieval,
real generation, real prompt).

**Fixed — an empty HTTP-200 response failed the farmer.** The chain treated empty
content as terminal *after* the loop, raising "I couldn't answer that one" while
three other models were available. Now a per-model bad attempt, like the
instruction-commentary case.

**Fixed — 429 burned the backoff budget.** A rate limit is per model, so retrying
the same model rarely helps; each one cost 3s+6s for nothing. 429 now moves
straight on. 5xx is still retried.

**⚠️ Reverted — disabling reasoning. My hypothesis was wrong.** The model spends
hidden reasoning tokens, and on a *short* test prompt disabling it looked like a
clear 2x win (21.2s → 10.1s). **Against the real prompt it was the opposite**:
13.6s/14.2s with reasoning vs 29.4s/25.5s without, because without a planning step
the model rambles and emits *more* output tokens (1016 vs 421). The short-prompt
test was not representative and nearly shipped a two-fold regression. Reasoning
stays on, with the numbers recorded in `llm.py`.

Also added a 90s chain ceiling and a 45s per-request cap — seven models × 60s is a
seven-minute worst case.

**After:** median 19.5s, max 37.3s, **0 failures in 6**. The latency itself is the
free tier's generation speed, not the code; the paid tier is the fix.

## Design audit against a rural-first brief

Owner asked for a screen-by-screen audit against a detailed rural-first design
brief. Two blockers surfaced before any design work:

1. **No screenshots arrived** — captured all seven screens myself at 390px.
2. **The brief's palette contradicts what we shipped.** It specifies light green

3. **The brief's nav (Home/Crops/Weather/Market/Profile) would remove features** —
   Assistant, Upload and Community — contradicting its own "do not remove any
   existing features" rule, and adds two that do not exist.

### ⚠️ Worst finding: the crop picker offers 12 crops, the model diagnoses 3

`frontend/lib/validation/auth.ts` offers **Tomato, Wheat, Potato, Rice, Maize,
Onion, Brinjal, Chilli, Cotton, Sugarcane, Groundnut, Soybean**.
`backend/app/models/labels.py` has ten classes across **Tomato, Potato, Pepper**.

So **nine of twelve selectable crops cannot be diagnosed** — a farmer picks Rice,
photographs a rice leaf, and gets a tomato/potato/pepper disease name,
confidently. And **Pepper, which IS supported, is not in the list at all**.
Home then shows the chosen crops in the header, so the UI *advertises* the
capability it lacks.

Not a crash — a plausible wrong answer, which is worse. Already a known limitation
(§4.1); what was new is that the UI invites it. Fix proposed: drive the picker from
the model's class list, show the rest disabled with "coming soon". Open question
flagged: is `Chilli` meant to map to the `Pepper` class?

### Measured compliance (390px, DOM-measured)

- **0 targets below 44px** — the project's own floor held.
- **46 targets at 44px rather than the brief's 48dp** — every one exactly 44, so
  it is a single token (`--spacing-tap`), not 46 fixes.
- **Body text is 14px on Home and Assistant**; brief floor is 16–18sp.
- **No sticky primary action on any screen.** Home has *no* primary action at all —
  the main task ("photograph a sick plant") has no door; the only route is the
  `Upload` tab, and "Upload" is jargon for this audience.
- **Language toggle on 1 of 6 screens**; brief wants it on every screen.
- **No offline cache or "data from last sync" banner.**
- **No voice input anywhere** — the biggest lever for low-literacy users.
- Home cards have **no image thumbnail**; brief asks for image + title + takeaway.

## Phase 12 — light green theme applied

Owner decided: **green and white for the farmers**, keep the animations.

Reverted the dark violet from Phase 11 back to the brief's rural-first palette —
`#2E7D32` leaf green on `#FAFAF5` off-white. Recorded in `DECISIONS.md` §12.
**The motion system was untouched** — `Reveal`, `TiltCard`, `SpotlightCard`,
`Marquee`, `RotatingText`, `Counter` were never palette-specific, so all of Phase
11's animation work carried over.

### Swapping hex values is not a theme change

Four things had to be **re-derived**, and each would have shipped a bug if I had
only recoloured:

1. **Glows invert in meaning.** A 0.4 bloom over near-black is a light source; the
   same over off-white is a stain that breaks every text contrast on it. Orbs
   rebuilt at **0.07–0.14**, grid backdrop 0.18 → 0.05.
2. **Glass stops earning its cost.** `backdrop-filter` is expensive on budget
   Androids, and translucent-white-on-off-white just looks dirty. Cards are now
   **solid white + soft shadow** — which is also what the brief asked for.
   Translucency kept only where content is genuinely behind it.
3. **One green does both jobs.** `#2E7D32` is 4.9:1 as text *and* 5.1:1 as a fill
   under white text, so `--color-primary` and `--color-accent` are the same value
   here. On dark they had to differ. The `ui-audit` assertion "accent and primary
   stay distinct" was therefore asserting a **falsehood** — replaced with the
   contract that matters: **white must be legible on the CTA fill** (5.13:1).
4. **Amber is a trap.** `#FFB300` is light — white on it is 1.9:1. Dark ink only.

### 44px → 48px was genuinely one token

The audit found 46 controls at exactly 44px, all from `--spacing-tap`. Raising it
to 48 fixed all 46. Two did **not** come from the token and had to be found by
measurement: the landing mobile menu toggle (`size-11`) and the upload
remove-photo button (`size-10`, 40px). `ui-audit`'s floor moved 44 → 48.

### ⚠️ A token whose value encodes a canvas assumption

The landing mockup used `bg-natural-text` with dark ink — right on dark (light
teal), became **dark-on-dark** on light (`#1B5E20`). Only re-deriving the pairing
catches that; a rename would not.
